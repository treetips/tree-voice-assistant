# 更新操作をヘッダーへ移し、アプリとツールを別リリースで更新する

- ステータス: Accepted
- 更新通知の見た目と操作配置は [ADR 026](./026-rex-style-update-status-pill.md) で置換
- 影響範囲: 更新UI、更新サービス、ツール配布、Releaseワークフロー、変換処理
- 関連: ADR 009、ADR 017、ADR 018、tree-image-optimizer ADR 0076・0078

## 背景・課題

更新カードは左サイドナビの最下部にあり、更新ありをクリックすると確認ダイアログを開いていた。ダウンロードから再起動までの進捗をカードで確認できず、失敗時の再実行もできなかった。また、アプリ本体とツールの更新を同じ配布経路で扱うため、ツールだけの更新をアプリのバージョン変更なしで公開できなかった。

tree-image-optimizer は Superlogical Rex を参考に、Download ボタンから進捗表示、ステージング、明示的な再起動までをヘッダー右端の1行カードにまとめている。本プロジェクトでも同じ操作感を採用する。

## 決定

### Releaseの分離

- アプリ本体は `vMajor.Minor.Patch` の通常リリースとして公開し、従来どおり `releases/latest/download/update-info.json` を参照する。
- ツールは `tools-latest` の事前リリースとして公開する。アプリのバージョンやタグは変更しない。
- アプリReleaseの成果物はアプリZIP、`update-info.json`、アプリ用の `SHA256SUMS.txt` に限定する。
- ツールReleaseの成果物は `tools-info.json`、ツール単位ZIP、ツール用の `SHA256SUMS.txt` に限定する。
- ツールReleaseを事前リリースに保つことで、GitHubの「Latest」はアプリ本体のままにする。
- アプリRelease作成前に `tools-latest/tools-info.json` を取得できることを検証する。

### ツールの範囲と初回準備

- ツールReleaseは `uv`、`mlx-audio` のプロジェクト定義・lockfile、`Irodori-TTS` のソース・プロジェクト定義・lockfileを配布する。TTSプロジェクト定義は取得失敗時の動的調達に備え、アプリ内リソースにもフォールバックを保持する。
- Python仮想環境と音声モデルは引き続き初回利用時に取得する。CIのPython絶対パスを利用者環境へ同梱すると再配置で壊れるためであり、大容量モデルをアプリ起動時に強制取得しないためでもある。
- 起動時に不足ツールをSHA-256検証付きで準備し、その後でローカルの `.installed.json` と配布メタデータを比較する。
- 既存環境で `.installed.json` が無い場合は、動的調達していた現行バージョンを初期値にする。`Irodori-TTS` は配布時の固定リビジョンへ一度更新される。
- ツールの準備・更新中はSTT/TTSの新規実行を無効化し、実行中はツール更新を開始できないようにする。

### ヘッダー右端の更新操作

- 詳細ペインのツールバー右端（`.primaryAction`）に、アプリとツールを統合した1行のカプセル型 Liquid Glass を表示する。サイドナビ下部の更新カードは削除する。
- 更新ありの文言は「アプリの更新があります」「ツールの更新があります」「アプリとツールの更新があります」の3種類とする。
- 確認ダイアログを挟まず、更新ボタンから利用可能な更新を開始する。両方ある場合はツールを更新してからアプリのダウンロード・ステージングを行い、ツール更新に失敗した場合はアプリ更新を開始しない。
- アプリ更新は Download → 受信バイト数の進捗 → SHA-256検証 → 展開 → ステージング → 緑の完了カードという流れにする。`/Applications` の置換は完了カードの「アプリ再起動する」を押した後だけに行う。
- ステージング中は実行中のバンドルを置換しない。再起動せずに終了した場合は次回起動時にステージングを掃除する。
- ツールだけの更新ではアプリを再起動しない。失敗時は赤いカードと「再実行」を表示し、未完の更新を同じ順序でやり直せるようにする。
- 更新なしカードもヘッダーへ移し、従来どおりクリックまたは10秒後に非表示化する。

## 代替案

- サイドナビに更新カードを残す
  - 却下: 幅が足りず、ラベルとボタンをRexと同じ1行にできないため。
- アプリとツールを同じReleaseに残す
  - 却下: ツールだけの配布にアプリのバージョンとタグが必要になり、更新頻度の違いを吸収できないため。
- ツールReleaseを通常リリースにする
  - 却下: GitHubの「Latest」がアプリでなくなり、既存の更新情報取得経路を壊すため。
- 配置後に自動再起動する
  - 却下: 完了カードで再起動のタイミングを確認できず、Rexのフローと異なるため。
- ツール更新を変換処理と並行実行する
  - 却下: 実行中のPython環境やバイナリを置換する可能性があるため。

## 結果

- 更新確認から再起動までをヘッダー右端の1行カードで操作できる。
- アプリ本体とツールを別々のRelease URLで確認し、ツールだけをアプリのバージョン変更なしで更新できる。
- 両方の更新がある場合はツールを先に完了させ、失敗時にアプリ更新へ進まない。
- ADR 017とADR 018のサイドナビ更新カードに関する決定を置き換える。ADR 009の配布方針は、ツール分離とRex風フローの部分を本ADRへ委ねる。
